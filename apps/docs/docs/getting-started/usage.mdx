Add Sponsor Gated Support to a GitHub Actions workflow so that gated issues stay open only for <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsors</Terminology>, exempt users, and recognized contributors, and only the issue opener and <Terminology title="Your own people, so they skip the sponsor check entirely" to="/docs/reference/terminology#authors-and-insiders">insiders</Terminology> can comment on them.

## Prerequisites

- **GitHub Sponsors enabled** — Your account (personal or organization) is enrolled in GitHub Sponsors. The sponsor list can be empty.
- **Repository access** — You have write access to the repository where the workflow will run.
- **<Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">Personal access token</Terminology> created** — A classic <Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">PAT</Terminology> with permission to read your <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology> data is stored as a repository secret. See [Personal Access Token](/docs/reference/personal-access-token/) for step-by-step creation instructions.

## Basic Workflow

Create a file named `sponsor-gated-support.yml` under `.github/workflows` with the contents below. You can adjust each input by following the [Inputs](/docs/reference/inputs/) reference.

```yaml title=".github/workflows/sponsor-gated-support.yml"
name: "Sponsor Gated Support"

run-name: "Running a task to analyze support issues"

on:
  issue_comment:
    types:
      - "created"
      - "edited"
  issues:
    types:
      - "opened"
      - "closed"

permissions:
  contents: "read"
  issues: "write"

jobs:
  check-issues:
    runs-on: "ubuntu-latest"
    steps:
      - name: "Checkout repository"
        uses: "actions/checkout@v7"
      - name: "Check support issues"
        uses: "mrjackyliang/sponsor-gated-support@v2"
        with:
          GITHUB_PERSONAL_ACCESS_TOKEN: "${{ secrets.PERSONAL_ACCESS_TOKEN }}"
          GITHUB_WORKFLOW_TOKEN: "${{ secrets.GITHUB_TOKEN }}"
          ISSUE_LABELS: "${{ vars.ISSUE_LABELS }}"
          ISSUE_LIMIT_COMMENTER: "${{ vars.ISSUE_LIMIT_COMMENTER }}"
          ISSUE_LOCK_ON_CLOSE: "${{ vars.ISSUE_LOCK_ON_CLOSE }}"
          ISSUE_MESSAGE_NOT_SPONSOR: "${{ vars.ISSUE_MESSAGE_NOT_SPONSOR }}"
          ISSUE_MESSAGE_WELCOME: "${{ vars.ISSUE_MESSAGE_WELCOME }}"
          IS_ORGANIZATION: "${{ vars.IS_ORGANIZATION }}"
          SPONSOR_ACTIVE_ONLY: "${{ vars.SPONSOR_ACTIVE_ONLY }}"
          SPONSOR_EXEMPT_FILE_LOCATION: "${{ vars.SPONSOR_EXEMPT_FILE_LOCATION }}"
          SPONSOR_MINIMUM: "${{ vars.SPONSOR_MINIMUM }}"
```

The workflow triggers on `issue_comment` (created, edited) and `issues` (opened, closed). It requires `contents: read` so checkout can read the exempt file and `issues: write` so the action can post comments, close issues, and lock threads.

Keep the `actions/checkout@v7` step if you use a `SPONSOR_EXEMPT` file, because the action reads it from your repository. Without the checkout, the action continues with an empty exempt list.

All remaining inputs beyond the two tokens are GitHub variables (`vars.*`), not secrets. You can configure them under **Settings > Secrets and variables > Actions > Variables** in your repository. Any variable you leave unset is passed as an empty value and falls back to its documented default, so you only need to create the variables you want to change.

## Tokens

The action uses two separate tokens, each with a distinct role. Both are referenced from the `secrets` context.

- **`GITHUB_PERSONAL_ACCESS_TOKEN`** — A <Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">personal access token</Terminology> you create and store as a repository secret (e.g., `secrets.PERSONAL_ACCESS_TOKEN`). The action uses it to query the GitHub Sponsors API for your sponsor list, filtered by the `SPONSOR_ACTIVE_ONLY` and `SPONSOR_MINIMUM` settings.
- **`GITHUB_WORKFLOW_TOKEN`** — The automatic `GITHUB_TOKEN` that GitHub Actions provides on every run (referenced as `secrets.GITHUB_TOKEN`). The action uses it to perform moderation tasks like posting comments, closing issues, and locking threads.

Separating the tokens keeps the <Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">PAT</Terminology> scoped to read-only <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology> data while the <Terminology title="GitHub's built-in token; moderation shows as github-actions" to="/docs/reference/terminology#tokens-and-setup">workflow token</Terminology> handles write operations against the repository. The <Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">PAT</Terminology> doesn't need write access to your repositories.

## Custom Messages

You can personalize the messages the action posts by setting two GitHub variables in your repository settings.

- **`ISSUE_MESSAGE_WELCOME`** — Posted when a <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology>, an exempt user, or an <Terminology title="Your own people, so they skip the sponsor check entirely" to="/docs/reference/terminology#authors-and-insiders">insider</Terminology> opens a gated issue. It defaults to a thank-you note confirming their sponsorship and letting them know the issue will be reviewed.
- **`ISSUE_MESSAGE_NOT_SPONSOR`** — Posted when a non-sponsoring user opens a gated issue. It defaults to a notice explaining that only <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsors</Terminology> can open issues and asking the user to become a <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology> first.

Both values support Markdown formatting, so you can include links, emphasis, and line breaks to match your project's tone. If you leave either variable unset, the action uses the built-in default message.

## Label Scoping

The `ISSUE_LABELS` input controls which issues the action gates. It accepts a comma-delimited list of label names and defaults to `support`.

- When set to a single label (e.g., `support`), only issues carrying that label are checked for sponsorship.
- When set to multiple labels (e.g., `support,bug,question`), any issue carrying at least one of those labels is gated.
- When left empty, the value falls back to `support` and issues with that label are still gated.

<Terminology title="Only gated-label issues are checked; the rest stay open" to="/docs/reference/terminology#issues-and-labels">Label scoping</Terminology> lets you run the action alongside other workflows without affecting issues that don't need <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology> verification. If your repository lives under a GitHub organization rather than a personal account, you can set `IS_ORGANIZATION` to `true` so the action queries the organization's <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology> list instead of the user's.

For the full list of inputs with their types, defaults, and valid values, see the [Inputs](/docs/reference/inputs/) reference.
