Keep gated support issues open for <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsors</Terminology>, contributors, and exempt users, and close and lock the ones everyone else opens, so your support time goes to the people who fund and build the project.

## Why Use This Action?

- Gates only the issue labels you configure (default: `support`) so bug reports and feature requests stay freely accessible.
- Checks the issue author against your live GitHub Sponsors list so access decisions stay current without manual updates.
- Welcomes <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsors</Terminology> with a configurable message when they open an issue, giving them immediate confirmation that their request was received.
- Recognizes contributors and collaborators automatically so people who build the project don't need a sponsorship to get help.
- Supports an <Terminology title="Your free-pass list: these users count as sponsors" to="/docs/reference/terminology#sponsors-and-eligibility">exempt file</Terminology> of usernames so you can grant access to anyone, no sponsorship required.
- Moderates comments on gated issues by removing posts from non-<Terminology title="Your own people, so they skip the sponsor check entirely" to="/docs/reference/terminology#authors-and-insiders">insiders</Terminology>, keeping the conversation focused between the author and your team.
- Locks gated issues on close (with `ISSUE_LOCK_ON_CLOSE`) so resolved threads don't attract drive-by comments.
- Enforces sponsorship thresholds so you can require active status and a minimum monthly <Terminology title="The monthly price a sponsor picked, checked against your minimum" to="/docs/reference/terminology#sponsors-and-eligibility">tier</Terminology> amount.
- Works on both user-owned and organization-owned repositories so teams and solo maintainers use the same setup.

## How It Works

When an issue event fires, the action runs through a short decision flow before taking any moderation steps. It uses two tokens: a <Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">personal access token</Terminology> to read your <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsors</Terminology> from the GitHub API, and the workflow's built-in token to moderate issues so actions appear under the "github-actions" bot instead of your account.

### Label Check

The action reads the issue's labels and compares them against your configured list (default: `support`). If none of the <Terminology title="Put this label on an issue and the sponsor check kicks in" to="/docs/reference/terminology#issues-and-labels">gated labels</Terminology> are present, the action exits and the issue proceeds normally.

### Author Check

For issues carrying a <Terminology title="Put this label on an issue and the sponsor check kicks in" to="/docs/reference/terminology#issues-and-labels">gated label</Terminology>, the action checks the author's relationship to the repository. Members, owners, contributors, collaborators, and users listed in the <Terminology title="Your free-pass list: these users count as sponsors" to="/docs/reference/terminology#sponsors-and-eligibility">exempt file</Terminology> pass without sponsoring you.

### Sponsor Check

Each run first queries your GitHub Sponsors list through the GraphQL API, paging through all <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsors</Terminology> and optionally filtering for active-only status and a minimum <Terminology title="The monthly price a sponsor picked, checked against your minimum" to="/docs/reference/terminology#sponsors-and-eligibility">tier</Terminology> amount in cents. An author who isn't an <Terminology title="Your own people, so they skip the sponsor check entirely" to="/docs/reference/terminology#authors-and-insiders">insider</Terminology> or exempt user passes only if they're on that list.

### Outcome

- **Allowed** — A <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology>, an exempt user, or an <Terminology title="Your own people, so they skip the sponsor check entirely" to="/docs/reference/terminology#authors-and-insiders">insider</Terminology> gets your welcome message, and the issue stays open.
- **Not a <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsor</Terminology>** — The action posts your not-sponsor message, closes the issue, and locks it.

After the initial check, the action continues to moderate the issue's lifecycle. When `ISSUE_LIMIT_COMMENTER` is `true`, comments on gated issues from anyone other than the issue opener or an <Terminology title="Your own people, so they skip the sponsor check entirely" to="/docs/reference/terminology#authors-and-insiders">insider</Terminology> are automatically deleted. <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">Sponsor</Terminology> or exempt status alone doesn't let someone comment on another person's issue. When `ISSUE_LOCK_ON_CLOSE` is `true`, gated issues are also locked when closed.

## Getting Started

1. Create a <Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">personal access token</Terminology> with `read:org` and `read:user` scopes, then store it as a repository secret.
2. Add the action to a workflow file that triggers on `issues` and `issue_comment` events.
3. Pass both the <Terminology title="Your own token, used only to look up who sponsors you" to="/docs/reference/terminology#tokens-and-setup">personal access token</Terminology> and the workflow's built-in `GITHUB_TOKEN` to the action so it can fetch <Terminology title="Someone paying you on GitHub Sponsors, so they get support" to="/docs/reference/terminology#sponsors-and-eligibility">sponsors</Terminology> and moderate issues separately.
4. Configure the workflow variables for your labels, messages, and sponsorship thresholds.
5. Optionally create a `SPONSOR_EXEMPT` file in your repository root to list usernames that bypass the sponsorship requirement.
